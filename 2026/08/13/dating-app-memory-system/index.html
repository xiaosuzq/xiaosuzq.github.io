本系列调研 dating app 记忆系统的设计，整体结构：

  • Graphiti走了一遭：时序知识图谱，离”陪聊记忆”还差多远
  • 让 AI 拥有”自我”,而不只是”记忆” —— Letta 的记忆即上下文
  • eros-engine的分层记忆：让AI记住”人”，而不只是”话”

调研目的

  1. 为 dating app 的记忆系统的设计提供参考
  2. 学习市面上常见的记忆系统的设计，不同场景下面，记忆系统该如何设计？

Dating app 背景

  1. 形态：数字人陪聊

    BH（真人）× DH（AI 数字人）。DH 用 LLM 生成”像真人”的回复。

  2. 关系养成型

    初始是陌生人，聊久了产生感情并配对。时间跨度以月计，不是一次性问答。

  3. 反导流（双向）

    DH 不主动引导用户离开；同时检测并阻断用户发的联系方式。后果很关键：所有互动只能沉淀在平台自己的库里 → 对话历史无限增长、且永不流失。

  4. “像真人”是体验命门

    DH 能不能记住久远的细节、说话前后一致、有自己的生活，直接决定沉浸感——这是产品的核心竞争力，不是可选项。

  5. 实时 + 低成本

    聊天要快（延迟敏感），成本要可控。

总结

由哪个特点 推出什么条件 一句话
关系养成 + 像真人 精确一致性 DH 说过的必须记得住，不能自相矛盾（精确记忆，不能抽错）
反导流 → 历史无限增长 可扩展分层 不能全量注入，必须短期/中期/长期分层
记忆的本质 精确检索 vs 语义检索 深刻的事精确记，不重要的事只留”模糊印象”、语义召回
实时聊天 低延迟 + 确定性注入 记忆注入不阻塞；且由 Hook 确定注入，不是让 LLM 自主拉
像真人 + 有自己的生活 时效性/生命周期 记忆会演进、会过期（LifeEvent 7 天 TTL）、有冷却

Mem0

本节分析参考开源项目 Mem0（Apache 2.0 协议）。

项目定位

Mem0 是给 AI 应用/Agent 提供”长期记忆能力”的中间件。它自己不聊天、不思考，它负责让”会聊天的 AI”变得”记得住你”。

项目核心设计

1. 写记忆过程

先看入口：两种模式。add() 有一个开关参数 infer，决定走哪条路：

  • infer=True（默认）→ 走完整流水线：LLM 提炼成事实
  • infer=False → 跳过 LLM：每条消息直接存原文

infer=False 很简单：每条消息 embedding 一下直接存，不做任何”理解”。下面重点讲默认的 infer=True 路径，它分 7 个阶段（Phase 0~7）。

Phase 0：上下文收集

取最近 10 条消息（从 SQLite messages 表）。作用：帮 LLM 理解指代。比如新对话只有一句”它后来好了吗”，LLM 需要知道”它”指的是什么——靠的就是前面这 10 条消息。

这也是为什么之前看到 SQLite 里有个 messages 表只留最近 10 条——就是给这一步当上下文用的。

Phase 1：检索已有记忆（关键，反直觉）

  1. 把「整段新对话」向量化
  2. 拿这个向量去库里搜 top_k=10 条最相关的旧记忆
  3. 把旧记忆的真实 UUID 映射成 “0”、”1”、”2” 短序号

两个细节值得注意：

  • 用”整段对话”当查询，而不是逐句查——因为要一次把”这段对话可能和哪些旧记忆有关”都捞出来。
  • UUID → 短序号映射（源码注释写的是 “anti-hallucination”）：真实的记忆 ID 是很长的 UUID，直接喂给 LLM，LLM 输出时容易编造不存在的 UUID。映射成 “0”、”1” 再喂进去，LLM 输出后再映射回来。

Phase 2：LLM 提炼（核心中的核心）

把「已有记忆 + 新对话 + 最近 10 条消息」拼成一个 prompt 调一次 LLM，让它返回：

这一步有三个关键点：

  1. 单次调用、批量产出：一次 LLM 调用，把整段对话里所有值得记的事实一次性吐出来，不是逐句调。
  2. 只 ADD、不 UPDATE/DELETE：prompt 明确告诉 LLM”你的唯一操作是 ADD”（ADDITIVE_EXTRACTION_PROMPT）。这就是”只增不减”的落地。
  3. LLM 同时干三件事：提炼新事实 + 判断是否重复（参考已有记忆）+ 给出链接关系（linked_memory_ids 指向相关旧记忆）。

Phase 3：批量向量化

把 Phase 2 提炼出的所有事实，一次性 embedding（失败则退化成逐条 embedding，工程上的兜底）。

Phase 4 + 5：哈希去重（第二道防线）

这里是去重的真正落地，且是”精确匹配”：只有文本逐字相同（MD5 相同）才会被跳过。”怕失败”和”害怕失败”两条，MD5 不同，都会存。

所以去重其实是两层防线：

  • Phase 2 的 LLM 被 prompt 要求”别重复提炼”——软约束（靠模型自觉，能挡大部分语义重复）
  • Phase 4/5 的 MD5——硬约束（只挡逐字相同的）

Phase 6：双写持久化

  1. 批量 insert 进向量库（向量 + payload）
  2. 批量写 SQLite 的 history 表（event=ADD）

两个存储各存一份：向量库是”活的记忆”（供检索），SQLite 是”审计日志”（供回溯）。注意这两步是分开的、非原子的——中间失败会造成两边不一致（有逐条 fallback，但不是事务级的）。

Phase 7：实体链接

  1. 从所有新事实里批量抽取实体（人名、地名、宠物名…）
  2. 全局去重（同一个实体跨多条记忆只存一次）
  3. 把实体写进”实体库”（第二个向量 collection），并挂上它关联的 memory_id 列表

作用：给未来的”读取”提供实体信号——检索时命中实体，就能把关联记忆一起 boost。

“先检索、再提炼”（Phase 1 → 2）：检索不是为了”找东西给用户”，而是给 LLM 提供”我已知道什么”，让它做去重和链接。这是它和”直接调 LLM 存记忆”的本质区别。

单次 LLM + 只增不减：老版本要调两次 LLM（提炼 + 决定增改删），新版本砍成一次、只做 ADD。省成本，但把”冲突”留给了读取侧。

去重是”软 + 硬”两层：LLM 语义去重（软）+ MD5 精确去重（硬）。中间有缝隙——语义重复但措辞不同的，会漏进去共存。

2. 读记忆过程

先看入口：search(query, filters, top_k, threshold=0.1) —— 拿一个问题、一个身份范围（user_id 等）、要几条、一个最低分门槛，去翻记忆。

9 步流水线：

Step 1：预处理 query

  1. 词形还原 query（lemmatize）→ 给关键词检索用
  2. 从 query 里抽实体（extract_entities）→ 给人名/地名等命名实体用

（这里的词形还原和实体抽取都是调用了 spaCy 这个框架来完成的）

一个 query 要提前加工成两种形态：一种给”关键词匹配”，一种给”实体匹配”。

Step 2：query 向量化

query → embedding 成一个向量，这是给”语义检索”用的。

Step 3：语义检索（故意多捞）

注意这里故意”多捞”：假如要 top_k=10 条，它实际先捞 60 条做候选池。因为后面要融合三路信号，得先有一个足够大的候选池，再重新排序。先宽捞、再精排。

Step 4：关键词检索（BM25）

用 BM25 算法做精确词匹配。只有向量库支持才做（有些向量库不支持就跳过）。

Step 5：归一化 BM25 分数

原始 BM25 分是无界的（020+），用 sigmoid 函数压到 [0,1]，且 sigmoid 参数根据 query 长度自适应（词越多，中点越高）。为什么要归一化？因为下一步要加法融合，BM25 的分必须和语义分（01）在同一个量级，否则没法加。

Step 6：实体加分

如果 query 抽出了实体（比如”Poppy”）：

  • 对每个实体 → embedding → 去实体库搜（相似度≥0.5 才算命中）
  • 命中的实体 → 给它关联的记忆加分（boost 上限 0.5）

这就是”实体链接”在读取侧的作用：提到”Poppy”，把和 Poppy 有关的记忆都提权。

Step 7：构建候选集

从语义结果里构建候选，顺便过滤掉”已过期”的记忆（记忆可以设过期时间 expiration_date，过期的默认不返回）。

三个关键设计：

  1. 加法融合，不是加权平均——三个信号直接相加，谁强谁加分。
  2. “最大可能分”是动态的，取决于哪些信号活跃：
活跃信号 最大可能分
只有语义 1.0
语义 + BM25 2.0
语义 + 实体 1.5
三路全有 2.5

这样保证最终分始终落在 0~1，可比。

  1. 语义分是”门槛”（gate）：语义分低于 threshold（默认 0.1）的候选，直接排除，哪怕 BM25 或实体能给它加很高的分。

这个设计很关键：它坚持”语义相关是前提”，BM25 和实体只是”锦上添花的提权”，不能把语义上不相关的东西硬救回来。

返回的就是一句句”记忆事实” + 分数 + 身份标签，供你塞进 prompt。

三个最值得记住的设计点

  1. 先宽捞、再精排（Step 3 的 over-fetch）：要 10 条，先捞 60 条，融合排序后再取前 10。用”多捞”换取”排序更准”。

  2. 加法融合 + 语义门槛（Step 8）：三路信号相加，但语义分是硬门槛——语义上不相关的东西，关键词和实体再强也救不回来。这是它防止”关键词误命中”的保险。

  3. BM25 用 sigmoid 归一化（Step 5）：因为原始 BM25 分无界，必须压到 0~1 才能和语义分相加。且参数随 query 长度自适应（长 query 原始分天然更高，所以中点也调高）。

3. 记忆的形态

一条记忆 = 三个东西：一句人话 + 一个向量 + 一堆标签。

唯一要记住的一点：记忆本体是自然语言，不是结构化字段（不是 {name:"小雨", fear:"失败"}）。

  • 好处：灵活，什么都能表达；
  • 代价：不能精确查询（没法 WHERE 恐惧原因=…），只能靠语义相似度模糊匹配。

其余（hash、向量、时间戳这些标签）都是”辅助检索”用的，不是记忆内容本身。

4. 成本

“成本模型”回答一个问题：用 Mem0，钱和算力花在哪、谁贵谁便宜、能不能省。

核心结论：成本几乎全压在”写入”，而且大头是 LLM。

写入（add） 读取（search）
LLM 调用 1 次（提炼事实） 0 次
embedding 调用 2~N 次 1 次
成本级别 贵 便宜

关键事实：LLM 和 embedding 的价格差好几个数量级。一次 LLM 提炼（几毛到几块，取决于模型和 token 数），一次 embedding（text-embedding-3-small 是百万 token 几毛钱，单条记忆几乎可忽略）。

所以：写入贵在”那一次 LLM”，读取便宜在”只用 embedding、不碰 LLM”。

写入拆解：钱花在哪

一次 add()（默认提炼模式）的调用清单：

  1. 检索已有记忆 → 1 次 embedding（把整段对话向量化去搜）
  2. LLM 提炼成事实 → 1 次 LLM ← 成本大头在这
  3. 批量向量化新事实 → 1 次 embed_batch
  4. 实体链接 → N 次 embedding（实体也要向量化存实体库）

结论：一次写入 ≈ 1 次 LLM + 若干次 embedding。embedding 那几笔几乎可以忽略，真正的账单就是”那一次 LLM”。

读取拆解：为什么便宜

一次 search() 的调用清单：

  1. query 向量化 → 1 次 embedding
  2. 语义 + BM25 + 实体检索 → 向量库本地检索（无外部 API）
  3. （可选）rerank → 默认关，开了才有额外调用

结论：一次读取 ≈ 1 次 embedding，零 LLM。这是刻意设计出来的——还记得之前说的”query 不做改写”吗？原因就是：改写要调 LLM，会让读取变贵，所以它拒绝。

三个影响成本的开关

  1. V3 把写入的 LLM 从 2 次砍到 1 次：老版本写入要调两次 LLM（先提炼、再决定增改删），新版改成”ADD-only 单次调用”。这是它最大的成本优化——代价是放弃了”修改/删除旧记忆”的能力（也就是”冲突只能推迟，不能消解”）。

  2. infer=False 可以彻底跳过 LLM：add(messages, infer=False) 时不提炼，直接存原文，零 LLM 成本。代价是失去”提炼”的质量——存的是原始消息，不是干净事实。

  3. 读取侧全程不碰 LLM：不 query 改写、rerank 默认关，都是为了守住”读取零 LLM”这条线。

项目短板

  1. query 不改写 —— 口语化、带指代、多轮追问的查询直接向量化，检索效果打折。代价是读取零 LLM，但召回质量押在 embedding 模型上。

  2. 成本随对话量线性增长 —— 每写入一次付一次 LLM 费，高频对话场景账单可观（前面刚算过）。

  3. 冲突只推迟、不消解（关系状态剧变的灾难）

ADD-only 只增不减，矛盾的旧记忆物理共存。暧昧→恋爱→分手，三条记忆会同时躺在库里，全靠”时间戳排序”猜哪个是当前状态。排序一旦错，数字人可能说出”我们还在一起呢”。

严格说不是”bug”，而是它主动做的设计取舍的代价：

  • 要省成本 → 只能 ADD-only → 冲突共存
  • 要省成本 → 只能精确哈希 → 语义重复共存
  • 要读取便宜 → 不做 query 改写

启发

1. 记忆重复和冲突的问题

记忆如果也是”只增不减”（恋爱 App 的对话记忆天然是累积的），那就必须回答”重复和矛盾怎么办”——Mem0 的答案是”写入前检索 + 链接”，也可以选”定期后台做冲突消解”或”读取时再做裁决”。三者各有代价。

“冲突消解放在写入还是读取”是一个关键架构决策。 Mem0 v3 选了”读取时裁决”来省成本，但代价是”矛盾的旧记忆永远物理存在”。对关系状态这种需要强一致、强覆盖的数据，你可能得在 Mem0 之上自己加一层”状态覆盖”（比如关系状态单独存一份权威值，不放进累积式记忆池），而不是完全依赖它的 temporal 排序。

凡是”会跳变、只能有一个当前值”的（关系、情绪状态），用覆盖式存储；凡是”只会累积”的（偏好、经历），才能用只增不减。

2. 成本控制

高频对话下，别每轮都调 LLM 提炼。设计”攒批 / 异步离线提炼 / 用便宜小模型”——把贵的那次 LLM 从用户在线路径挪出去。

3. 要不要做 query 改写

用户问法是口语化、带指代、多轮追问的，读取侧加一层 LLM 改写能显著提升召回。代价是读取变贵，要权衡（可以只对”检测到指代不清”的 query 改写）。

4. 存取的时候是存原文还是存提炼之后的数据

Mem0 的”智能记忆”不是免费的，它本质是用每次写入的一次 LLM 推理，换来了”对话被自动消化成干净事实”。在设计自己系统时，会面对同一个岔路口：

  • 追求省 token：写入时不做提炼，只存原文，等要用时再让 LLM 从原文里现捞（延迟转移到读取侧）
  • 追求检索质量：像 Mem0 这样，写入时就把事实榨干，读取时快而准（成本集中在写入侧）

Mem0 选了后者，并且用”单次调用、只增不减”把写入成本压到最低。这是它值得你记进报告的一个明确取舍。
