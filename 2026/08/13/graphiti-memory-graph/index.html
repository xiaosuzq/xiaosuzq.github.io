Graphiti走了一遭:时序知识图谱,离"陪聊记忆"还差多远

发表于2026-08-13|更新于2026-08-15|记忆系统调研Graphiti
|浏览量:

本文是《dating app记忆系统设计调研》的子文章，分析对象为开源项目 Graphiti。

项目定位

Graphiti = LLM 驱动的时序知识图谱引擎，专为 AI Agent 的长期记忆而生：自动从对话/数据里抽取实体和关系，增量织成一张带时间、可溯源的知识网，再用”语义 + 关键词 + 图遍历”混合检索取出来喂给 Agent。

知识图谱 vs 传统 RAG

核心区别一句话

普通 RAG 是”检索文档片段”，Graphiti 是”维护一张随时间演化的知识图谱”。前者回答”哪段文本相关”，后者回答”关于这件事，目前什么是对的、过去发生过什么”。

本质区别对照

维度 普通 RAG Graphiti
存什么 原文切片（chunk）+ 向量 结构化事实（实体→关系→实体）
检索方式 向量相似度（embedding） 语义 + BM25 + 图遍历 三者混合
时间 基本无（数据是静态快照） 每条事实有时间窗口，可查”任意时间点的真值”
更新 重嵌入/重建索引（批量） 增量更新，新数据实时融入
冲突处理 新旧版本并存或覆盖 旧事实自动”失效”但保留，历史可追溯
溯源 追溯到某文档 追溯到产生它的 episode（原始数据）
知识组织 扁平，无结构 有实体、关系、本体（可自定义类型）

具体拆开说

1. 检索粒度不同

普通 RAG 返回的是文本块，模型还得自己从一堆段落里重新理解。Graphiti 返回的是结构化事实，比如 Kendra --喜欢--> Adidas鞋子（截至 2026年3月），直接是知识而不是原文，Agent 拿到就能用。

2. 增量 vs 批量

普通 RAG 数据一变往往要重新分块、重新 embedding、重建索引。Graphiti 的 add_episode() 是把新对话/文档实时解析、和已有图谱去重合并（resolve_extracted_nodes），只更新受影响的部分。

3. 知识的组织方式

普通 RAG 是一堆扁平的向量点。Graphiti 有图结构——实体之间通过关系相连，所以能做图遍历（比如”A 的同事的老板是谁”这种多跳问题），还能自定义本体（用 Pydantic 定义你关心的实体/关系类型），这是纯向量检索做不到的。

和 GraphRAG 比呢？

GraphRAG 比普通 RAG 进一步（也建图），但它主要用于静态文档的批量摘要（社区聚类 + 顺序 LLM 摘要），时间是基本的时间戳，查询延迟秒级到几十秒。Graphiti 则是为动态、高频更新的 Agent 场景设计的：增量、实时、亚秒级查询、自动事实失效。

② 三路并行召回

3. 记忆的形态

Graphiti 的”记忆”不是一段段文本，而是一张**”带时间的属性图”**——它由「实体、带时间窗口的事实、原始对话」三层编织而成，每件事都记着”何时为真”和”从哪听来的”。

一、记忆的完整形态：5 类节点 + 5 类边

五种节点对应”记忆”的五个不同部分：

节点类型 记忆隐喻 存什么关键字段
EntityNode 你记住的”人/物/概念” name、name_embedding、summary（动态简介）、attributes（自定义属性）
EntityEdge 你记住的”事实” fact（一句话事实）、fact_embedding、valid_at/invalid_at（时间窗口）、episodes（来源）
EpisodicNode “当初怎么知道的” content（原文）、valid_at（发生时间）
CommunityNode “同一圈子的人” summary（群体摘要）
SagaNode “一条叙事时间线” summary、first/last_episode_uuid

五种边就是把这些节点连起来的关系：

边 关系类型 连接 含义
EntityEdge RELATES_TO 实体→实体 知识本身
EpisodicEdge MENTIONS 对话→实体 溯源（这事实哪段话提的）
CommunityEdge HAS_MEMBER 社区→实体 归类
HasEpisodeEdge HAS_EPISODE 叙事线→对话 串时间线
NextEpisodeEdge NEXT_EPISODE 对话→对话 先后顺序

二、记忆的三层结构

这张图本质上是三层记忆，各司其职：

第 1 层：知识层（记住”什么”）

这是记忆的核心。每条边都是一条带时间戳的事实：

第 2 层：溯源层（记住”从哪来”）

每条知识都能追溯到”哪段原始对话产生的”。这就是为什么 Agent 答错时能查出处、能精确删除”只由某段对话产生”的记忆。

第 3 层：组织层（记住”怎么归类”）

社区是”自动聚类”出来的抽象记忆（类似”这一堆实体是关于健身的”）；Saga 是”一条叙事线”（比如”用户和 Kendra 的这段关系史”）。

四、两个贯穿全局的”形态特征”

① 时间融进了每条记忆

普通知识图谱存的是”当前快照”，Graphiti 每条事实都是一个时间区间：

旧事实不删除，只是打上 invalid_at。所以记忆的形态是立体的、带历史深度的，而不是一张”此刻”的平面快照。

② 向量融进了记忆

  • 实体的 name_embedding —— 用来”按名字/语义”找到这个实体
  • 事实的 fact_embedding —— 用来”按语义”找到这条事实
  • 实体的 summary —— 用来”按描述”字面检索到实体（和 name 一起建了全文索引）

所以每条记忆同时具备了”能被字面搜到、能被语义搜到、能被关系走到”三重可达性。

4. 成本模型

一、总览：成本分布

成本
写记忆（add_episode） 贵 —— 多次 LLM 调用
读记忆（search） 便宜 —— 基本不调 LLM，纯检索

这是它和 RAG 的根本成本差异：RAG 写便宜（切块存）、读贵（每次查询让 LLM 现场读一堆文本）；Graphiti 反过来，把 LLM 的成本一次性花在”写入时把知识组织好”，换取之后无数次查询的廉价。

二、写一次 episode 的成本明细

一次 add_episode 的 LLM 调用清单：

步骤 调什么 次数 用什么模型
③ 抽实体 extract_nodes 1 次 大模型
④ 实体去重 dedupe_nodes 0~1 次（只有疑似重复才调） 大模型
⑤ 抽边 extract_edges 1 次 大模型
⑥ 边解析/失效 resolve_extracted_edge 每条边 1 次 大模型
⑦ 抽属性 extract_attributes 每个自定义实体 1 次 small 模型
⑦ 摘要 extract_summaries_batch 每 30 个实体 1 批 small 模型

外加 embedding 成本：每个实体名、每条事实各生成一个向量。

关键洞察：写入成本不随”文本长度”线性增长，而随”抽出多少实体 + 多少边”增长。

  • 一段话抽出 3 个实体、2 条边 → 约 1+1+2 = 4~5 次 LLM 调用
  • 一段话抽出 30 个实体、25 条边 → 约 1+1+25+属性+摘要 ≈ 30+ 次调用

所以事实密度高、关系多的文本，写入成本陡增。边解析（resolve_extracted_edge）是最贵的部分——每条边都要单独和已有边比对一次。

三、读一次 query 的成本

步骤 成本
query 向量化 1 次 embedding
BM25 检索 无 LLM，图数据库全文索引
向量检索 无 LLM，数据库算余弦
BFS 遍历 无 LLM，图数据库遍历
RRF 融合 无 LLM，纯计算
cross-encoder 精排（可选） 有成本：query × top-k 候选成对打分，但只对 RRF 粗排后的少量候选

所以读记忆默认几乎零 LLM 成本（除非开启 cross-encoder 重排），延迟在亚秒级。这就是它能支撑”高频查询”的原因。

项目短板

短板 1（最致命）：写重读轻，而对话是高频的

一次 add_episode 要做 5~30+ 次 LLM 调用（抽实体、抽边、每条边解析、摘要），延迟秒级。

而 dating app 里，真人和数字人每条消息都是一次写入。这意味着：

  • 成本爆炸：一天几十轮对话，每轮多条消息，LLM 账单会非常吓人
  • 延迟不可接受：对话是实时的，用户发一句”我今天好难过”，你不能等 2 秒（几次 LLM 往返）才让数字人回应
  • 架构矛盾：Graphiti 假设”写入不那么频繁、查询很频繁”，dating 恰恰是”写入极高频、每次写入都要即时消费”

这是根本性的错配，不是调参能解决的。要么异步批量写入（牺牲实时性，数字人刚聊完不记得），要么接受高昂成本。

短板 2：记忆粒度错位——它记”事实”，不记”情感、语气、原话”

Graphiti 的核心动作是把对话抽取成结构化事实：

但 dating 场景真正需要记住的，恰恰是抽取过程中丢失掉的东西：

  • 原话：她说过的那句”你是我唯一的光”——需要能原样调出来，不是被抽象成”表达爱意”
  • 语气/情绪：这句话是撒娇、是认真、还是哽咽说的
  • 氛围/暧昧：关系现在处于什么状态，冷还是热
  • 承诺的措辞：”我们约定下周见面”这种，措辞本身就重要

Graphiti 的 summary 是有损压缩，实体摘要会把几十条情感事实压成一句”用户情绪敏感”。情感细节、原话、语气，都在抽取和摘要里被抹平了。它适合记”用户喜欢什么品牌”，不适合记”用户此刻的心理状态和你们之间的暧昧细节”。

短板 3：去重合并可能”张冠李戴”

dating 对话里人名、昵称、代称极多：”他””那个人””我前任””宝宝””她”。

Graphiti 靠”向量粗筛 + LLM 精判”判断”是不是同一个实体”。在 dating 场景，指代消解极难：

  • 用户说”他”——指的是数字人？还是她现实里的某个男生？还是前任？
  • 把”前男友”和”现男友”合并成一个节点 = 记忆被污染，且这种污染很难发现和修复

实体去重一旦出错，后果比 RAG 严重得多——RAG 顶多召回错了片段，这里是直接污染了图的结构。

启发

启发 1：记忆的标签很重要，不能只是记一个内容

记忆必须带”出处 + 时间”（Episode 溯源）

Graphiti 把”原始对话”当成一等公民存进图，每条事实都能追溯到”哪段对话说的”。这是 dating 记忆系统最该抄走的一点。

因为 dating 场景最怕的就是”张冠李戴”和”记错语境”——“她说想见面”这句话，是什么时候、什么语气、什么上下文说的，决定了数字人该怎么回应。

落地：每条记忆都挂上 {原文, 时间戳, 上下文来源}。 宁可多存，不可只存”用户想见面”这条干巴巴的抽象——抽象是死的，出处是活的。

记忆要有”时间深度”（失效而非删除）

Graphiti 用 valid_at/invalid_at 记事实的时间窗口，旧事实不删、标记失效。

dating 记忆的核心恰恰是”变化”：”她以前喜欢爬山，最近不爱提了””关系从热络到冷淡”。只存”当前状态”会丢掉这段演变轨迹，而演变轨迹本身就是最宝贵的记忆。

落地：记录偏好、情绪、关系状态的”变化历史”，而不是覆盖。 回答”她最近和三个月前有什么不同”应该变成一等能力。

启发 2：去重合并做的时候要考虑清楚

去重合并要”谨慎”，不是”激进”

Graphiti 靠向量 + LLM 把”疑似同一实体”合并。dating 场景人名/昵称/代称极多，合并错了会污染记忆且难发现。

落地：借鉴它的”分层判断”（先便宜过滤再昂贵精判），但默认策略改成”存疑就分开”。 宁可有”宝宝”和”她”两个节点、事后用规则合并，也不要把”前男友”和”现男友”误合成一个。

第 1 层：全文索引 = 倒排索引

把”文本”预先拆成”词 → 出现在哪些文档、各几次”的一张倒排表：

好处：查询时不用扫全库，直接查”哪些事实含这个词”，一步缩小到候选集合。

第 2 层：BM25 = 给候选打分排序

对每条候选事实 D，算：

  • IDF（逆文档频率）：词越稀有 → 分越高。Kendra 只在 5 条事实里出现，值钱；”喜欢”在 8 万条里出现，不值钱。
  • TF（词频）：这词在这条事实里出现越多 → 分越高，但有饱和、且长文档会被惩罚（长度归一化）。

为什么能”直接”排序：倒排表里已经存好了词频 f(qi,D)，索引级存好了总文档数 N、文档频率 n(qi)、平均长度 avgdl —— BM25 公式需要的全部数据都在表里，查表 + 套公式即可，不用现算。

一句话总结：Graphiti 把每条事实边当一篇”文档”，建库时用倒排索引存好”词 → 出现位置+词频”；查询时把用户的问题也分词，查倒排表筛出含相关词的事实，再用 BM25 公式（稀有词加分、高频词饱和、短文档不吃亏）给它们打分排序，返回最相关的事实边。

它在整个检索里扮演的角色：提供”字面精确匹配”这一路，和”向量语义匹配””图遍历关系推理”互补——因为有的查询靠字面就能命中（人名、专有名词），有的靠语义（换个说法），有的靠关系（多跳推理）。三路合起来，就是 Graphiti 说的”混合检索”。
