定时任务选型总结

发表于2026-08-15|更新于2026-08-16|定时任务
|浏览量:

定时任务选型，本质是逐级缩小范围：先看单机还是多实例，再看要互斥还是分片，最后才决定要不要上平台。本文按「进程内 → 分布式互斥 → 分布式平台」三层，用标签页展开，每层讲原理、注意事项、最佳实践，最后给一套选型决策时间线和常见坑。

这一层解决「单个进程内跑定时任务」的需求，不涉及多实例协调。

Spring @Scheduled

底层原理

执行链路分三步：

  1. 注册：@EnableScheduling 导入 ScheduledAnnotationBeanPostProcessor，在 Bean 初始化后扫描所有带 @Scheduled 的方法，每个注解解析成一个 ScheduledTask，注册进 ScheduledTaskRegistrar。
  2. 调度：ScheduledTaskRegistrar 最终交给一个 TaskScheduler 执行。Spring Boot 自动装配的默认实现是 ThreadPoolTaskScheduler，内部包装一个 ScheduledThreadPoolExecutor，其任务队列是 DelayedWorkQueue（按「下次到期时间」排序的堆）。
  3. 触发：工作线程阻塞在队列头，到期后取出执行，再计算下次到期时间重新入队。
注解 下次触发时间基准 等价 JDK API
fixedRate 上次开始时间 + period scheduleAtFixedRate
fixedDelay 上次结束时间 + delay scheduleWithFixedDelay
cron 日历表达式计算 CronTrigger（Spring 自己的 CronExpression）
  • fixedRate 不看实际耗时：如果单次执行超过 period，下次触发会被「挤压」到紧接着上次结束，但不会并发（同一任务串行），只会连发。
  • fixedDelay 天然防重入，因为间隔从结束时刻算。
  • cron 走的是 Spring 自带的 CronExpression（6 段：秒 分 时 日 月 周），不是 Quartz 的 7 段实现，边界语义有差异。

注意事项

  1. 默认单线程：所有 @Scheduled 任务共享一个线程，串行执行——一个任务阻塞，其余全部卡死。生产务必配 pool.size。
  2. 异常会导致该任务静默停止：任务方法抛异常后，这个任务的后续调度被取消，且不报错。所以方法体要么自己 try/catch，要么给 TaskScheduler 配 ErrorHandler。
  3. fixedRate vs fixedDelay 要分清：可能超时、或不想重入的任务用 fixedDelay。
  4. 多实例会重复执行：注解是进程内的，多个实例各跑一遍。要互斥就得进第二层（ShedLock）。
  5. 自定义 TaskScheduler bean 会顶掉自动装配：此时 spring.task.scheduling.pool.size 失效，得在代码里手动设线程池。

最佳实践

① 显式配置线程池（默认只有 1 个线程）

② 异常兜底：要么方法内 catch，要么配全局 ErrorHandler

注意：一旦自定义 TaskScheduler bean，spring.task.scheduling.pool.size 就失效了。

③ 按需选触发方式：怕重入用 fixedDelay，要严格频率用 fixedRate

④ 触发时间外置到配置，改 cron 不用改代码

⑤ 优雅停机：等正在跑的任务收尾

⑥ 多实例部署必须配 ShedLock（衔接第二层，否则每个实例都跑一遍）

JDK ScheduledExecutorService / Timer

底层原理

ScheduledExecutorService（推荐）：核心实现 ScheduledThreadPoolExecutor，和一个 DelayedWorkQueue 堆。它按任务下次执行时间排序，到期取出执行；scheduleAtFixedRate 按「计划时间 + period」、scheduleWithFixedDelay 按「实际结束 + delay」重算下次入队。

Timer（不推荐）：单线程 + 单个 TaskQueue 堆。所有任务共用一个线程，任何一个任务阻塞或抛未捕获异常，整个 Timer 里剩余的所有任务全部失效。功能被 ScheduledExecutorService 完全覆盖，现在基本只出现在老代码里。

两者和 Spring 的关系：Spring @Scheduled 默认调度器就是包了一层 ScheduledThreadPoolExecutor，所以原理完全相同。

注意事项

  1. 异常静默停止（最关键的坑）：周期任务抛异常，ScheduledFutureTask.runAndReset() 不再 re-schedule，后续调度被取消且无任何提示。必须自己 try/catch。
  2. Timer 三大坑：单线程阻塞、异常即全灭、无优雅停机保证——新代码一律别用。
  3. scheduleAtFixedRate 连发：单次超过 period 时不并发，但会连续「补跑」，任务堆积。怕重入用 scheduleWithFixedDelay。
  4. 线程池大小要匹配：池太小长任务饿死其他任务，池太大浪费资源。
  5. shutdown vs shutdownNow：shutdown 等当前 tick 跑完更安全；shutdownNow 中断正在执行的任务，可能留下半成品状态。

最佳实践

① 异常必须吞：任务抛异常会静默终止调度

② 周期任务优先用 scheduleWithFixedDelay 防连发

③ 优雅停机：先 shutdown 等待，超时再 shutdownNow

④ Java 21 用虚拟线程工厂

⑤ 把「异常吞掉 + fixedDelay + 优雅停机」封装成基类复用

⑥ 别用 Timer

这一层解决第一层的核心缺陷：@Scheduled 是进程内的，多实例部署时任务会在每个实例重复执行。方案分两类——ShedLock 只做「互斥」（同一时刻只跑一份），Quartz 在互斥之外多了持久化、misfire 补偿和运行时动态管理。

Spring @Scheduled + ShedLock

底层原理

定位：ShedLock 解决 @Scheduled 的分布式缺陷——注解调度是进程内的，多实例部署时同一个任务会在每个实例上各跑一遍。ShedLock 在调度方法外面套一层分布式锁，让同名任务同一时刻全集群只有一个实例执行，其余实例跳过本轮。

关键边界：ShedLock 只做互斥，不做分片、不做负载均衡——抢到锁的实例跑全部数据，其余实例本轮空转。

组件模型：三个核心抽象：

组件 作用
LockProvider 锁后端抽象。同一套注解，锁状态可以存在 JDBC（PG/MySQL 表）、Redis、ZooKeeper、Mongo 等不同地方
LockConfiguration 一次加锁的完整参数（name、lockAtMostFor、lockAtLeastFor 及派生出的两个时间点）
SimpleLock lock() 成功后返回的句柄，承载 unlock()

AOP 拦截链路：@SchedulerLock 通过 AOP 切面工作：

  1. @EnableSchedulerLock 注册一个 BeanPostProcessor。
  2. 扫描所有含 @SchedulerLock 方法的 Bean，用 MethodInterceptor 包一层代理。
  3. 方法被调用时，拦截器在方法体执行前先调 lockProvider.lock(config)。
  4. 拿到锁 → 执行方法体 → finally 里 unlock()；拿不到 → 跳过方法体，记一条「not executed」日志。

注意：因为是 AOP 代理，同一 Bean 内的方法自调用会绕过代理，导致锁不生效。

分布式锁的原子获取：

  • JDBC（JdbcTemplateLockProvider）：锁状态存在 shedlock 表（name PK / lock_until / locked_at / locked_by）。首次 INSERT 靠 name 主键唯一约束占坑；后续 UPDATE ... SET lock_until = ? WHERE name = ? AND lock_until <= ?——lock_until <= now 这个条件是关键，锁还没过期则 UPDATE 命中 0 行，返回抢锁失败。usingDbTime() 让「now」取 DB 时钟，消除时钟偏差。
  • Redis（RedisLockProvider）：锁是一个带 TTL 的 key。SET lock:name value NX PX <lockAtMostFor 毫秒>——NX 保证 key 不存在才写入（抢锁成功），PX 设 TTL（持锁实例崩溃，锁自动过期，不永久死锁）。

两个时间参数的确切语义：

参数 作用 约束
lockAtMostFor 锁的硬上限（TTL / lock_until）。持锁者崩溃也会到期自动释放，防死锁 必须 > 任务最长执行时间
lockAtLeastFor 锁的最短持有时间。任务提前跑完，unlock() 也等到该时刻才放锁 必须 > 集群内最大时钟差

lockAtLeastFor 专门对抗时钟偏差：多实例时钟有偏差时，A 实例「以为」锁该放了、提前释放，B 实例立刻抢到，造成两个实例短暂重叠。

一次完整执行时序：

注意事项

  1. name 必须全局唯一：不同任务共用同名锁会互相抢锁，导致本该并行的两个任务变成互斥。
  2. lockAtMostFor 必须大于任务最长执行时间：否则任务还在跑，锁已过期，另一实例抢到锁后并发执行，互斥失效。
  3. lockAtLeastFor 必须大于集群最大时钟差：取值小了，时钟偏差导致的短暂重叠仍然会发生。
  4. Bean 内自调用绕过代理：methodA() 内部直接调 this.methodB()，而锁在 methodB 上，锁不会生效。把锁挪到最外层被 @Scheduled 直接触发的方法上。
  5. JDBC provider 要先建 shedlock 表（官方有 schema），且注意时区统一。
  6. 互斥 ≠ 分片：ShedLock 只保证「不重复跑」，不能「多实例并行加速」。
  7. 别拿 ShedLock 当通用分布式锁：它是为「调度方法互斥」设计的，粒度是「任务名」。业务里的临界区应该用 Redisson 这种通用分布式锁。
  8. 锁后端的可用性 = 任务的可用性：JDBC/Redis 一旦不可用，抢锁会失败，任务会被跳过。

最佳实践

① 命名带服务前缀，避免跨服务撞名

② 参数取值：lockAtMostFor 给 2 倍冗余，lockAtLeastFor 给秒级对抗时钟差

③ provider 按现有依赖选，别为锁引新中间件

④ JDBC 用 usingDbTime()（见上）——把「now」交给 PG 时钟，所有实例对比同一把尺子。

⑤ 给「跳过执行」留信号：抬高 ShedLock 日志级别

⑥ lockAtMostFor 不是慢任务的兜底

Quartz

底层原理

定位：Quartz 是一个独立的调度框架，不依赖 Spring。相比 @Scheduled，它多出三块能力：持久化（调度状态落库，重启不丢）、misfire 补偿（宕机期间漏触发的任务可补跑）、运行时动态管理（运行期增删任务，不改代码）。

组件模型：六个核心概念，关系是「Scheduler 用 JobStore 记录 Job/Trigger，用 ThreadPool 执行 Job」。

组件 作用
Job 业务逻辑，实现 org.quartz.Job 的 execute(JobExecutionContext)
JobDetail Job 的元数据封装（name/group、JobDataMap、是否持久等）。JobDetail 是「定义」，Job 是「实例」
Trigger 触发规则：CronTrigger（日历）、SimpleTrigger（间隔/次数）、CalendarIntervalTrigger、DailyTimeIntervalTrigger
Scheduler 调度器，把 JobDetail 与 Trigger 关联并驱动执行
JobStore 调度状态存储。RAMJobStore（内存，默认）、JDBCJobStore（持久化，可集群）
ThreadPool 执行 Job 的工作线程池

关键区分：JobDetail 与 Job 不是一回事。JobDetail 是持久化的「任务定义」，而 Job 实例每次触发都重新 new 一个（JobFactory 反射创建），用完即弃。这决定了 Job 天然无状态。

执行链路：

  1. scheduler.start() 启动调度主线程（QuartzSchedulerThread）和线程池。
  2. 调度主线程循环：从 JobStore 取出「next fire time ≤ now」的 Trigger。
  3. 触发：通知监听器，把 Job 交给线程池执行。
  4. 执行：JobFactory 反射 newInstance() 一个 Job，调 execute()。
  5. 收尾：更新 Trigger 的 next fire time，把本次触发写进 QRTZ_FIRED_TRIGGERS 历史表。

持久化与 JobStore：默认 RAMJobStore 把一切存在内存，进程一重启，Job/Trigger/触发历史全部丢失。生产要换 JDBCJobStore，把调度状态落到 11 张 QRTZ_* 表。持久化的意义不只是「重启恢复」：它让调度状态脱离单个进程，是集群、misfire 恢复、动态管理的地基。

misfire 补偿机制：「misfire」= 本应触发的任务，因调度器宕机或线程池已满而没触发。Quartz 检测到 now - 计划触发时间 > misfireThreshold（默认 60s）即判定 misfire。每个 Trigger 有一组 misfireInstruction 策略：

  • MISFIRE_INSTRUCTION_FIRE_ONCE_NOW：立即补跑一次。
  • MISFIRE_INSTRUCTION_DO_NOTHING：跳过，等下个周期。
  • MISFIRE_INSTRUCTION_IGNORE_MISFIRES：全补（可能堆积）。
  • SMART_POLICY（默认）：由 Quartz 按 Trigger 类型挑一个合理策略。

这是 @Scheduled 完全没有的能力——@Scheduled 宕机期间的任务就是永久丢了。

集群机制：开启 isClustered = true 后，多个 Quartz 实例共享同一个 JDBCJobStore。抢 Trigger 靠数据库行锁（对 QRTZ_LOCKS 表 SELECT … FOR UPDATE），保证同一个 Trigger 同一时刻只有一个节点触发。节点宕机，其他节点通过 check-in 检测（集群心跳），接管死亡节点的 Trigger，实现失效转移。

Quartz 集群能同时做到「不重复执行」和「节点挂了有人接手」，比 ShedLock 完整。但代价是依赖数据库锁，会给 DB 带来额外负载，且依然是单点执行全部数据，不是分片。

注意事项

  1. 默认 RAMJobStore 重启丢调度：生产要持久化/集群，必须换 JDBCJobStore 并建 11 张表，这一步漏掉是最常见的「上线即丢任务」事故。
  2. Job 每次执行都新建实例：成员变量跨次调用不保留，状态必须放 JobDataMap 或外部存储。
  3. cron 是 7 段式（秒 分 时 日 月 周 年），比 Spring @Scheduled 的 6 段多一个可选「年」；且日/周用 ? 表示互斥。
  4. misfire 策略要显式配置：默认 SMART_POLICY 的行为未必符合预期。
  5. 集群依赖数据库锁 + DB 时钟一致：各节点时钟偏差大会导致 misfire 判断错乱。
  6. 集群本质不是分片：同一 Trigger 仍只有一个节点跑，不会多节点并行加速。
  7. 动态管理能力是双刃剑：运行期改任务，也意味着任务定义不再「代码即真相」。
  8. 接入成本高：没有持久化/misfire/动态管理需求时，它是过度设计。

最佳实践

① 生产必配持久化 + 集群，schema 交给 Flyway 管

② Job 保持无状态，需要参数走 JobDataMap

③ 用 JobBuilder / TriggerBuilder 声明式定义，7 段 cron 记得补字段

④ 关键任务显式配置 misfire 策略，别依赖默认

⑤ 需要防并发执行时，注解声明

⑥ cron 段数对照（迁移时最容易错）

框架 段数 示例（每天 3 点）
Spring @Scheduled 6 段：秒 分 时 日 月 周 0 0 3 * * *
Quartz CronTrigger 7 段：秒 分 时 日 月 周 年 0 0 3 * * ?

⑦ 集群环境统一时钟 + 显式 misfireThreshold

前两层的共同局限：要么只管单进程（第一层），要么只做互斥、不做并行分摊（第二层）。第三层是独立的调度平台，核心价值是两点——分片并行（把一批数据拆成 N 片，N 个执行器各跑一片）和可视化治理（后台动态改 cron、手动触发、失败重试、告警、执行日志）。代价也很明确：新增中间件，要单独部署 + 运维。

XXL-Job

底层原理

定位：国内最流行的分布式调度平台，开源（许雪里），架构是「调度中心 + 执行器」两段式。调度中心（xxl-job-admin）是独立的 Web 应用，提供控制台；执行器（xxl-job-executor）作为依赖嵌入业务服务。

架构与通信：

  • 调度中心（admin）：负责管理任务、按 cron 触发、路由策略、失败重试、告警、日志存储。
  • 执行器（executor）：嵌入业务服务，接收 admin 指令、执行 JobHandler、回调结果。
  • 两者通过 HTTP 通信（底层 xxl-rpc，基于 Netty）。执行器启动后定期向 admin 心跳注册。

核心概念：

概念 作用
JobHandler 任务逻辑，实现 IJobHandler 接口，用 @XxlJob(“name”) 注解注册
BEAN 模式 任务逻辑写在执行器代码里（推荐）
GLUE 模式 任务逻辑在 admin 控制台在线编辑（Groovy），运行期编译执行
路由策略 第一个 / 轮询 / 随机 / 一致性哈希 / 最不经常使用 / 故障转移 / 忙碌转移 / 分片广播
阻塞处理策略 单机串行 / 丢弃后续调度 / 覆盖之前调度

一次调度流程：

  1. admin 的调度线程（内部基于 Quartz 触发 cron）扫描到期任务。
  2. 按路由策略选一个执行器节点。
  3. 发 HTTP 请求（携带任务参数、分片参数）。
  4. 执行器线程池执行 JobHandler。
  5. 执行器回调 admin 记录执行日志。
  6. 失败 → 按配置重试次数重试 → 仍失败则告警。

分片广播（最关键的能力）：路由策略选「分片广播」时，admin 把任务广播给所有执行器节点，每个节点拿到自己的 shardingIndex / shardingTotal。业务代码据此只处理属于自己的那一片数据，实现「多实例并行分摊同一批数据」——这正是前两层都做不到的。

注意事项

  1. 新增中间件：admin 要单独部署、单独数据库，加一套运维成本。
  2. 网络与时钟：执行器要与 admin 网络互通，且时钟一致。
  3. GLUE 模式是双刃剑：在线改代码方便，但导致「代码即真相」失效，生产建议只用 BEAN 模式。
  4. 分片广播 ≠ 自动分区：分片只是「告诉你 index/total」，怎么切数据要业务自己实现。
  5. 任务和业务服务强绑定：任务编排、跨服务调度能力有限。
  6. 依赖 admin 可用性：admin 宕机，定时触发停止（执行器本身不自治）。

最佳实践

分片广播处理批数据（核心用法）

执行器配置

关键任务开失败重试 + 告警：在 admin 后台给任务配置失败重试次数（如 3）、告警邮箱。别让失败任务静默。

生产只用 BEAN 模式，禁用 GLUE，保证任务逻辑在代码库、可 review、可回滚。

如何选型？

定时任务选型的本质是逐级缩小范围，每个问题对应一层，答完一个才进入下一个：

第一步：单机还是多实例？

这是最大的一道分叉，决定要不要离开第一层。

  • 单机 / 单实例（或明确不会水平扩容）→ 直接 @Scheduled，结束。再往下都是过度设计。
  • 多实例 → 进第二步。

第二步：要「互斥」还是「分片」？

这是第二层和第三层的分界线，也是最常被混淆的一步。

  • 互斥：一份数据，只要有一个实例跑、别人别碰 → @Scheduled + ShedLock，结束。
  • 分片：一批数据，多个实例并行各跑一片、提速 → 必须上第三层平台，跳到第四步。

第三步：只要互斥，要不要「持久化 / misfire / 动态改」？

（仅针对选了「互斥」的人）

  • 三样都不要 → ShedLock，最省，结束。
  • 要持久化（重启不丢调度）、要宕机补跑、要运行期增删任务 → Quartz（集群模式）。

第四步：上平台后，要不要「任务编排 / 分布式计算」？

（仅针对选了「分片」的人）

  • 纯定时 + 分片 + 可视化后台 → XXL-Job。
  • 还要 DAG 编排 / MapReduce 计算 → PowerJob。

判断标准：你关心的是「别重复跑」，还是「跑得更快」？ 前者互斥，后者分片。

有什么容易踩的坑？

1. 反直觉：绝大多数团队停在第二层就够了。

分片是「数据量大到单实例跑不完」才有的需求，互斥才是常态。ShedLock + @Scheduled 覆盖了 90% 的定时任务场景。上 XXL-Job 意味着要养一套 admin + 数据库 + 运维，别为了「看起来专业」过度设计——这是选型里最常见、代价最大的错误。

2. 「互斥」和「分片」是两码事，ShedLock 不解决分片。

ShedLock 抢到锁的实例跑全部数据，其余实例空转；分片是让实例各跑一片、合起来更快。

3. 定时任务常见反模式：

  • 用定时轮询去模拟「事件驱动」（该发消息的不发，靠扫表凑合）。
  • 定时任务里跑长事务，拖垮 DB 连接池。
  • cron 写死在代码里，改一次发一次版。
  • 单实例阶段不配 ShedLock，扩容那天才发现任务重复跑。
  • 任务失败没有告警，静默停摆数周无人知。

4. 可观测性是最容易漏的一环。

定时任务「跑没跑、跑多久、成没成功」必须有信号：@Scheduled 里加执行耗时日志、ShedLock 抬高日志级别看「跳过」、平台方案看控制台执行记录。一个没有监控的定时任务，和没有定时任务一样危险。

5. 边界提醒：本文只覆盖「定时」，不覆盖「延时」。

「每 5 分钟扫一遍」是定时（周期触发），「15 秒后做某件事」是延时（单次延迟）。后者的选型完全不同——进程内 TaskScheduler / RocketMQ 延迟消息 / Redis ZSet 延迟队列 / DB 任务表，那是一个独立的话题。
