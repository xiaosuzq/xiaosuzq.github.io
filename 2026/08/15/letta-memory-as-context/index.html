让 AI 拥有"自我",而不只是"记忆" —— Letta 的记忆即上下文

发表于2026-08-15|更新于2026-08-15|记忆系统调研Letta
|浏览量:

本文是《dating app记忆系统设计调研》的子文章，分析对象为开源项目 Letta。

项目定位

Letta Code 是一个”让 AI agent 拥有自我”的运行框架（agent runtime）。

注意，不是”给 agent 加记忆”——Claude Code 也有记忆。它的真正主张是：把 agent 的”身份 + 记忆 + 经验”本身，做成一个 agent 自己拥有、可改写、跨时间延续的”自我”。

它到底”新”在哪

传统 agent（含 Claude Code）的记忆，主语是”任务/用户”；Letta 的记忆，主语是”agent 自己”。

项目范式

它代表了一个范式转向，可以用三个关键词概括：

1. 「记忆即上下文」（memory-as-context）

主流范式把记忆当外部数据库：历史存向量库，用 RAG 按需捞回来。Letta Code 的范式是：记忆就是”每次醒来看到的上下文”本身，而 agent 可以直接改写这段上下文。

这是最根本的转向：从”给模型加一个记忆数据库”，变成”让模型拥有并改写自己的自我”。它的金句就是那句 “the model is the engine; you are the tokens”。

2. 「自我进化靠重写上下文」（self-evolution, not retraining）

传统上”让 AI 变强”靠的是重训权重（慢、贵、不在 agent 手里）。Letta Code 的范式是：学习发生在 token 空间——agent 通过改写自己的 memory blocks、skills、prompts、甚至 harness 本身（mods）来进化。训练换成”重写自己的上下文”，于是学习变成 agent 自己能随时做、可审计、可回滚的事。

3. 「睡眠期计算 / 离线巩固」（sleep-time compute）

它把 agent 的计算拆成两个阶段：

  • 在线：跟用户实时交互
  • 离线：轮次之间，后台”做梦”（reflection）去巩固记忆、提炼偏好、消解矛盾

这直接来自它的研究背景（sleep-time compute 论文），也是它和”一锤子对话”式 agent 的范式区别——记忆的维护是一个后台持续运行的过程，不是一次性的读写。

两种”记忆修改”的本质区别：

  • 如果你的流程是”存对话 → LLM 分类 → 存库 → 下次按需检索”，那你的”记忆修改”只是整理索引，DH 不会因此更懂 BH——它只是检索更快了。
  • 如果改成”存对话 → 改写 DH 的人设/关系层 → 下次无条件在场”，那才真正做到了”DH 越聊越懂 BH”。

对关系养成型产品，后者才是命门——因为”一致地记住久远的细节”这件事，靠检索是脆弱的（漏了就没记起来），靠”已经改进的自我”才是稳的。

项目核心设计

1. 写记忆流程

写记忆分两条流水线，一条是自动的（agent 无感），一条是主动的（agent 自己干）。它们同时跑，互不干扰。

流水线 A：对话历史（自动记录）

要点：这条线全程不需要 agent 主动做任何事。用户说的、agent 回的，每一句都被自动、全量地记下来。这就是”对话本身怎么记住”的答案——不是 agent 主动记的，是 harness 自动记的。

流水线 B：agent 主动触发

这条线是 agent 主动的，有三个触发入口，但最终都汇入同一条”改文件 → commit”的底层。

触发入口（三选一）：

  1. 在线主动写：对话中 agent 判断”这个值得记”
  2. /remember：用户显式说”记住 X”
  3. 后台做梦：对话结束后 reflection 子代理离线整理

① 决策：写到哪一层

这是写之前唯一需要做的判断。规则就一条：

  • 如果这条信息决定”我是谁 / 我怎么对待这个人” → 写进 system/ 目录，变成常驻 Memory Block。
  • 如果只是个可检索的细节 → 写进其它目录，变成按需档案。

代码里这个映射是死的（local-backend.ts 的 memoryBlockPath）：system/ 开头的文件才是常驻块，其它路径自动归为档案。文件路径本身，就是它的记忆层级。

② 执行写操作：两条路

路 A：memory 工具（主路径，agent 在线时用）

这是 agent 对话中”随手记”的方式，一个工具搞定。它支持六种原子操作：

操作 作用
str_replace 替换文件里的一段文字
insert 在指定行插入
create 新建文件（可带初始内容 + description）
delete 删文件或目录
rename 重命名（比如档案提升为常驻块）
update_description 只改描述，不改内容

关键点：它自动 commit。agent 不需要自己跑 git 命令，工具改完文件顺手就提交了，而且提交的 author 是 agent 自己的身份（<agent_id>@letta.com）。

还有一个 memory_apply_patch 工具，是它的”进阶版”——用 codex 风格的 patch 格式（*** Update File + @@ 差异块）一次性改多处，同样自动 commit。

路 B：直接编辑文件（大改动时）

当改动很大——比如要重构整个目录、一次重写好几个块——就用 Bash/Edit 直接编辑 $MEMORY_DIR 里的文件，然后手动 git commit（author 要填 agent 身份）。

两条路的本质一样：都是改文件 + commit。区别只是 memory 工具帮你把 commit 自动化了。

③ 格式校验（写之前的护栏）

不管哪条路，改记忆文件都要过三道校验：

  1. 路径必须在记忆目录内——相对路径按内存目录解析，绝对路径只有在 $MEMORY_DIR 内才接受，外面的路径一律拒绝（防止 agent 乱写系统文件）。
  2. 必须有 frontmatter——每个记忆 .md 文件开头要有 YAML，且 description: 字段非空（这行描述就是未来”读”的时候判断要不要打开的钥匙）。
  3. read_only 文件不能改——像 memory_filesystem 这种系统自动生成的块，禁止 agent 动。

④ git commit（写记忆 = 写代码）

这是整个设计里最有辨识度的一步：记忆的落盘，就是一个 git commit：

type 类似代码提交的语义：fix（纠正错误记忆）、feat（新增记忆）、chore（日常整理）。

好处就在这一步：git log 能看到”这段记忆是什么时候、被谁、因为什么改的”——记忆的完整演变史，可审计、可回滚。

⑤ 生效时机：写给未来的自己

最后一步，也是最反直觉的一步：这次写的，本轮对话用不上。

系统提示在对话开始时就编译好并缓存了（缓存键 = 原始提示哈希 + 记忆的 git revision）。你改完文件、commit 了，git revision 变了，但要等下一次编译——新开对话、或显式 recompile——新的系统提示才会把这些改动读进去。

写记忆的本质是：现在改文件，未来的自己才带上。 这就是它反复强调 “you are writing for your future self” 的原因。

2. 读记忆流程

读记忆分两个动作：一个是对话开始时”组装大脑”（编译），一个是对话中”缺啥捞啥”（检索）。

动作一：编译组装（每次对话开始时）

缓存优化：编译结果会被缓存。缓存键 = 原始提示哈希 + 记忆的 git revision。只要记忆没变（没有新 commit），就复用上次编译好的，不重新搬。

3. 记忆模型

记忆不是”外部数据库”，而是 agent 自己拥有、可改写、跨时间延续的”自我”（上下文）。金句：“the model is the engine; you are the tokens”——模型只是引擎，token 才是”我”。

三层模型（核心主体）

记忆被分成三层，划分的唯一维度是**”每次是不是必须知道”**：

层 内容 谁管 是否常驻上下文 能否改写
Recall（经验层） 全部对话原文 harness 自动 否（最近原文 + 旧摘要） 否，只增不改
Memory blocks（学习层） persona / human 等”自我”块 agent 主动 是（全内容） 是
External memory（知识层） skills / 文件 / 共享记忆 agent 主动 否（只有索引） 是

物理形态统一：三层都投影到同一个 git 仓库（MemFS）。system/ 目录 = 常驻块，其它目录 = 档案。记忆文件就是 markdown 文件，带 frontmatter。

两条铁律（模型的核心洞察）

  1. “自动记录” ≠ “主动学习”

    对话原文（recall）是 harness 自动、全量、被动记录的，agent 无感；memory blocks 是 agent 主动、有选择、提炼出来的。前者是”经历”，后者是”学习”。

  2. “检索层” ≠ “自我层”

    语义检索（RAG）负责发现细节（回忆某次具体对话）；自我性靠常驻层（”用户讨厌被叫小朋友”每次都在场）。所以：能被搜出来的，就别占常驻层。

四个设计原则

  1. 渐进式披露：上下文只放”核心身份 + 索引”，详细内容用到才展开。
  2. 记忆即代码：git 版本化 → 可审计（git log 看演变史）、可回滚、可跨机器携带。
  3. 写给未来的自己：改记忆不立即生效，下次”编译”才带上——写和当前对话解耦。

4. 成本模型

1. 每轮固定成本（跑不掉）

每轮对话 = 至少 1 次向量嵌入（把 DH 这条回复存进 recall 时向量化）。这是按轮次/消息条数计的固定项，跟 DH 记不记、回忆不回忆无关。

2. 变量成本（DH 行为决定）

DH 每主动记一条 → +1 次大模型；每回忆一次 → +1 次大模型 +1 次嵌入。这两项是”DH 越主动，成本越高”，不可预测，定价时要设上限或约束。

3. 摊薄成本（后台，按轮次摊）

后台做梦：每 N 轮跑 1 次 → +1 次大模型。压缩：历史超限时触发 → +1 次大模型。这两个按”每 N 轮摊一次”折进单轮成本。

最有价值的洞察：记忆改写有隐性成本

这是整个成本模型里最反直觉、也最值得写进文章的点：

改记忆会破坏 prompt cache（提示缓存）。

LLM 服务（如 Anthropic/OpenAI）会对”系统提示”做缓存——如果系统提示没变，后续轮次就不用重复付费处理它。但一旦你改了 memory block，系统提示就变了，缓存失效，那一轮就要重新处理整个提示。

所以”频繁改记忆”是有真实成本的。Letta 的应对策略：

  1. 用后台做梦做异步更新——在空闲时段改，而不是在线时随手改
  2. 批量更新，少写——攒着一起改，减少缓存失效次数
  3. 不重要的事写进档案层——档案层不在上下文里，写它不会影响缓存

这反过来印证了分层模型：常驻层的改写贵（动缓存），档案层的改写便宜（不动缓存）——所以”能被搜出来的就别放常驻层”不只是一个整洁性建议，更是一条成本纪律。

项目短板

短板 1：记忆质量全靠模型”自觉”，漏了就真漏了

Letta 没有独立的抽取管道，全靠 agent 自己判断”这个该不该记”。模型一旦漏判，重要信息就永久丢了。

对 DH 的启发：DH 的记忆不能只靠 DH 自觉。必须加一层确定性的兜底抽取——尤其是”雷区/红线”（比如用户说”我最讨厌被放鸽子”）这类必须记的，用规则 + 小模型强制抽取，不能赌 DH 记不记得。

短板 2：自我改写是把双刃剑，身份会漂移

agent 能改自己的 persona，但改坏了身份就崩了。代码里其实写了防护（”changes should be incremental to avoid complete loss of self”），恰恰说明这个风险是真实的。

对 DH 的启发：DH 的”人设”要拆成两层——

  • 核心人设（性格、语气、三观）：锁死，不让 DH 自己改，由你们产品侧控制；
  • 关系理解层（对这个 BH 的了解、偏好）：才让 DH 演化。

否则聊着聊着，DH 的性格会漂走，产品一致性崩掉。

短板 3：语义检索会漏，跨月叙事天然脆弱

Letta 自己也承认”一致性靠常驻层，不靠检索”——反过来就是，凡是要靠检索才想起来的东西，都存在”漏掉”的风险。

对 DH 的启发：这是你产品的命门。结论只有一个——决定关系走向的关键状态，必须进常驻层（无条件在场），检索只做补充。别指望”语义检索”能保证 DH 三个月后还记得你们第一次约会的关键细节。

启发

1. 记忆不能只靠自觉，要有确定性兜底。

DH 的记忆不能只靠 DH 自觉抽取有用信息。必须加一层确定性的兜底抽取——尤其是”雷区/红线”（比如用户说”我最讨厌被放鸽子”）这类必须记的，用规则 + 小模型强制抽取，不能赌 DH 记不记得。

2. 人设要分层，核心锁死、关系层才演化。

DH 的”人设”要拆成两层——核心人设（性格、语气、三观）锁死，不让 DH 自己改，由产品侧控制；关系理解层（对这个 BH 的了解、偏好）才让 DH 演化。否则聊着聊着，DH 的性格会漂走，产品一致性崩掉。

3. 关键状态进常驻层，检索只做补充。

决定关系走向的关键状态，必须进常驻层（无条件在场），检索只做补充。别指望 DH 自动触发的检索索引文件，能保证 DH 三个月后还记得你们第一次约会的关键细节。
