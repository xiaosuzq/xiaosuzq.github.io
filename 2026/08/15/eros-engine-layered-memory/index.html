eros-engine的分层记忆：让AI记住"人"，而不只是"话"

本文是《AI Agent 长期记忆系统设计调研》的子文章，分析对象为开源项目 eros-engine。

项目定位

一个开源的 Rust 引擎，给「AI 数字人陪聊」产品提供有状态的核心——让一个数字人能跨上千轮、跨数月地「记住同一个人、关系持续演进、始终人设在线」。

项目范式

架构形态：模块化 Monorepo + 严格向下依赖

这是一个 Cargo workspace，四个 crate，依赖方向只允许向下：

范式关键词：「纯领域内核 + 接口隔离的集成 + 薄编排壳」。

  • core 不依赖任何框架、不做任何 I/O——affinity、ghost、PDE、persona 这些”逻辑大脑”是纯函数。
  • llm 和 store 是两个独立、可替换的集成层（换 embedder 是配置变更，换向量库是换 store crate）。
  • server 只负责”粘合”——把请求接进来、编排一下、分派出去。

这个形态的直接收益：core + llm + store 可以当库被别的产品直接 cargo add 复用，不用继承它的 HTTP 形状、Postgres schema、JWT auth。

项目核心设计

1. 写记忆过程

写记忆发生在回复已经发给用户之后——引擎不会让「记账」耽误用户看到回复。整个写记忆一共三条线。

先交代背景：一次聊天的完整闭环

用户发一句话给数字人，引擎干的事是这样的：

  1. 用户那句话先存进 chat_messages 表（原始文字，不加工）。
  2. 引擎生成数字人的回复，回复也存进 chat_messages 表。
  3. 回复用 SSE 流推给用户。
  4. 到这里，用户已经看到回复了。之后，引擎才在后台启动一个任务（post_process），去”记账”——写记忆就是其中一件事。

所以「写记忆」永远发生在第 4 步，是异步的、滞后的、不阻塞回复的。

线一：实时写入（每一轮都做，原样存）

这条线做的事最简单：把用户这句话原封不动地变成一条记忆，不做任何理解、不分类。

第 1 步：判断这一轮值不值得记。要同时满足两个条件才记：

  • 用户这句话不是空的（用户真的说了点什么）；
  • 数字人至少回了一句非空的话。

第 2 步：只取「用户说的话」，不取数字人的话。

这里有个铁律：只记用户说的，绝不记数字人自己说的。

原因是踩过坑的（issue #113）：如果数字人的话也存进记忆库，下一轮聊天时会把它当「记忆」召回、喂进数字人自己的提示词里——数字人看到”自己以前说过这句话”，就会一遍遍重复，回复直接卡死成一句车轱辘话。

第 3 步：把这句话变成一个「向量」。调 embedding 服务（默认 Voyage），把用户这句话变成一串 512 个小数——这串数字就是”语义指纹”。

第 4 步：把这句话写进两层（写两次）。同一句话、同一个向量，写进同一张表两次，区别在于一个字段 instance_id：

写第几层 instance_id 填什么 存的内容 含义
relationship 层 这个数字人的编号 用户：我养了一只猫 只有这个数字人能想起
profile 层 NULL（空） 我养了一只猫 所有数字人都能想起

注意 relationship 层会在前面加一个 用户： 前缀——这样将来召回时，数字人能看懂”这是用户说过的话”。

它的定位是「原样埋点」——便宜、快、每轮都做，保证”用户说的每句话都有机会被将来想起”，但它不做任何理解。

线二：后台提炼（空闲才做，用 LLM 理解）

线一只是”原样存”，不知道哪句话重要。真正该长期记住的是”他是做设计的、养了只猫、上个月换工作”这种稳定事实。这些靠线二提炼。

线二有个名字叫 dreaming-lite（”做梦”），是后台定时任务，每隔一段时间扫一次。

第 1 步：找”该被提炼的会话”。找同时满足两个条件的会话：

  • 空闲了：last_active_at 过了阈值；
  • 还没被提炼过：classified_at 为空。

它的定位是「空闲时的深度提炼」——用 LLM 把一段对话”消化”成几条稳定的、带类别的事实。

线三：结构化抽取（每一轮都做，但不进向量库）

  • 永远不会删——画像只会越填越全。

它的定位是「结构化画像」——不参与语义检索，是给匹配、给下游产品用的”可查询的用户档案”。

三条线串起来看

  • 线一保证”每句话都有机会被想起”，但没理解能力；
  • 线二在线一的基础上，空闲时”消化”出稳定的、带类别的事实；
  • 线三走的是另一条路，产出的是结构化画像，不参与向量检索。

三条线互相不抢、互不阻塞，合起来构成完整的”写记忆”。

2. 读记忆

读记忆发生在每一轮数字人要开口回复之前——目标只有一个：让数字人”想起”这一轮该想起来的事，塞进提示词。

第 1 步：确定「这一轮要查什么」

默认用用户这一轮刚说的那句话当查询种子。如果用户发的是图片，就用图片的文字描述当查询。

第 2 步：确定「查多少、查哪几层」

请求带 memory_scope 开关，决定注入哪些记忆。默认 neutral_and_relationship：

  • 注入中性的画像（不含感情观、兴趣这些亲密字段）；
  • 注入数字人专属记忆（relationship 层）。

关键点：这个开关只管”读不读”，不管”写不写”。就算这轮设成 none，该写的照样写进库。

第 3 步：把查询也变成「向量」

调 embedding 服务，把”我最近搬家了，好累”变成一串 512 个小数。兜底：如果开关全关或查询为空，跳过；embedding 失败也静默降级成”什么都没想起来”，绝不让记忆问题卡住回复。

第 4 步：三路并行去向量库里「捞」

用 tokio::join! 同时发起三个查询：

查询 内容 K 值
查询 1 已分类的 profile 记忆（按类别分组捞） 每类 2 条
查询 2 未分类的 profile 记忆（兜底） 4 条
查询 3 relationship 专属记忆 3 条

怎么判断”像不像”？余弦相似度，pgvector 直接排序返回前 K 条。

一个重要的设计选择：没有”相似度门槛”。无条件返回最像的前 K 条——哪怕这 K 条都跟当前话题关系不大。好处是简单、提示词长度可控；代价是可能捞到无关的（靠后面的分组和去重缓解）。

第 5 步：拼上结构化画像

把 human_insights 表的字段渲染成”基础画像”，插到所有记忆最前面。这块不经过向量检索，直接整行读出来。中性模式下会剥掉亲密字段。

第 6 步：跨层去重

同一句话可能既在 profile 层又在 relationship 层（线一写两层）。进提示词前做去重：规范化后如果两条一样，只留 profile 层那条。

第 7 步：渲染进提示词

去重后，把所有记忆渲染成带标题的文本块，塞进 system prompt：

兜底：什么都没捞到时，填入占位文案”（刚认识，还不了解他）”，而不是空着。

第 8 步（顺带）：短期记忆直接塞，不检索

最近的聊天记录（最近 20 条原文）直接按时间顺序塞进去，不做向量检索。长期记忆管”久远的、模糊的”，短期记忆管”刚刚发生的、精确的”。

串起来看

3. 记忆模型

记忆的数据模型核心一句话：记忆不存成一份大 JSON，而是拆成「一张向量表 + 一张结构化画像表」，前者管”模糊想起”，后者管”确定的事实”。

总览：三张表撑起记忆

核心表：companion_memories（向量记忆）

字段逐个讲：

字段 类型 含义
id UUID 主键，自动生成
session_id UUID（外键） 来自哪个会话，级联删除
user_id UUID 属于哪个用户（记忆的隔离维度）
instance_id UUID，可空 数字人编号（整个数据模型的灵魂）
content TEXT 记忆文本，塞进提示词的就是它
embedding VECTOR(512) 512 维语义向量
category TEXT，可空 类别标签（只有”做梦”提炼的行有值）
metadata JSONB，可空 不透明附加信息，引擎不解析
created_at 时间戳 创建时间

灵魂字段：instance_id —— 用「一个字段」区分两层记忆

整个数据模型最关键的设计：不建两张表，而是用 instance_id 是不是 NULL，来区分两层记忆。

  • instance_id = NULL → profile 层，跨数字人共享（”用户对花生过敏”，换哪个数字人都该知道）；
  • instance_id = 某个数字人的 id → relationship 层，只有这个数字人能想起。

配合两个部分索引，让两层各自检索都便宜：

“部分索引”：索引只建在满足 WHERE 条件的那些行上，查 profile 层只扫 profile 索引，查 relationship 层只扫 relationship 索引，互不干扰。

两种写入器，在数据模型上怎么区分

raw-turn 写入的行 dreaming 提炼的行
instance_id 两层都写（NULL 和数字人 id） 只写 profile 层（NULL）
content 用户原话（relationship 层带”用户：”前缀） LLM 提炼出的干净事实
category NULL（不分类） fact/preference/event/emotion/relation
metadata NULL 可能带（领域、置信度等 JSON）

所以光看一行的 category 和 metadata 是不是 NULL，就能判断它是”原样埋的”还是”提炼出来的”。一张表同时承载两种粒度的记忆——这是它数据模型上的巧劲。

第二张表：human_insights（结构化画像）

这张表跟向量记忆完全相反：全是 typed 列、没有向量、没有 JSON 大 blob。

三个数据模型上的特点：

  1. 一个用户一行（user_id 主键），画像只有”当前状态”，没有历史版本。
  2. 字段强类型：TEXT、TEXT[]、INT。
  3. 数组字段能直接查询（interests 建 GIN 索引，能直接做”兴趣集合重叠”查询）。

为什么这张表不做成向量？因为它存的是”确定的事实”（职业、城市、兴趣），用精确的字段匹配就够了，不需要”模糊召回”。向量记忆管”想起模糊的旧事”，结构化画像管”回答确定的事实”——两种数据模型各司其职。

第三张表：chat_messages（原料）+ chat_sessions（容器）

chat_messages 是原始聊天记录，是记忆的原料，本身不 embed。chat_sessions 有三个字段专门为”写记忆”服务：

  • last_active_at —— 判断会话是否空闲、该不该提炼
  • classified_at —— “已提炼”章，盖了就不重复
  • classification_claimed_at —— “正在提炼”认领标记，防止多实例抢同一会话

数据模型的设计哲学

设计 为什么
一张表用 instance_id 区分两层 两层共享同一套 schema，只是”归属”不同，省一张表
向量（模糊）和结构化（精确）分离 两种检索需求不该硬塞进一种存储
category/metadata 是「渐进式」加出来的 可空列、不用回填，先上线”原样埋”再慢慢加”提炼+分类”
metadata 存成不透明 JSONB 将来 prompt 加字段时不用改表
user_id 是逻辑外键，session_id 是物理外键 用户跨系统不建物理 FK；session 同 schema 建 FK 带级联删除
记忆生命周期绑定在会话上 会话没了记忆一起没，避免孤儿记忆

一句话总结数据模型：记忆 = 一张向量表 companion_memories（用 instance_id 一个字段切成”跨数字人的 profile 层”和”专属的 relationship 层”，用 category/metadata 的 NULL 与否区分”原样埋”和”提炼”）+ 一张强类型的画像表 human_insights（确定事实，不向量）。原料在 chat_messages，容器在 chat_sessions。核心思想是：把”模糊召回”和”精确查询”拆成两种完全不同的存储模型，而不是塞进一个大 JSON。

4. 成本模型

读路径：每轮固定要付的账

动作 次数 成本
embed_query（把当前这句话变向量） 1 次 便宜（embedding 远便宜于生成）
pgvector 语义检索（三路） 3 次查询 零外部成本（本地 DB）
读 human_insights 画像 1 次 零外部成本（普通 SQL）

读路径最大的成本其实是主回复那次 chat LLM，但那是”聊天”不是记忆的成本。记忆本身读路径只花「1 次 embedding」，非常轻。

关键点：读路径的 K 值很小（每类 2、兜底 4、专属 3），所以注入提示词的内容有硬上界，不会因为记忆越攒越多而让 prompt 越来越贵——记忆无限增长，但读的成本不随之增长。

写路径：每轮要付的账（在后台，不阻塞）

每轮付（fire-and-forget）：

动作 次数 说明
embed_document（写 relationship 层） 1 次 把”用户：X”变向量
embed_document（写 profile 层） 1 次 把”X”变向量
affinity 评估 LLM 1 次 小模型，短消息跳过
insight 抽取 LLM 1–2 次 两阶段；facts 为空只跑 1 次

空闲才付（dreaming 提炼）：

动作 次数 说明
memory_extraction LLM 每会话 1 次 贵，但只在会话空闲时跑
embed_document × 候选数 每条 1 次 只 embed 挑出的候选，不是全量

控成本的 8 个设计手段（精华）

手段 省的是什么
两档节奏：热路径只 embedding，冷路径才 LLM 提炼 把”理解”这件贵事摊销到空闲时段
fire-and-forget 写路径 LLM 不阻塞回复，成本只体现在钱
小 K + 无阈值 注入 prompt 的内容有硬上界
跨层去重 同一事实只注入一次，少付重复 token

项目短板

短板 1：存储只增不减，没有遗忘机制（最大的隐患）

整个系统只有 upsert，没有 delete。MemoryRepo 没有删除方法，human_insights 的注释还明写了 “deliberately no erase path”。companion_memories 会随聊天历史线性无限增长——反导流让数据只进不出，这是”机会”也是”炸弹”。

短板 2：检索没有「时间/重要性」权重，纯靠相似度

检索只按 embedding 余弦距离排序，created_at 存了但从不参与排序。导致：三年前说的”我讨厌猫”和昨天说的”我养了猫”权重一样，谁离查询近谁赢。真实记忆是有”新鲜度”和”重要性”的，这里完全没有。

短板 3：没有相似度阈值，可能注入无关内容

“纯 top-K，无阈值，最近的 K 条无条件返回”。好处是 prompt 长度可控，代价是可能召回完全不相关的东西塞进提示词，既浪费 token，又可能干扰数字人。

短板 4：写入侧不去重，靠读时兜底

同一句用户的话，每轮既写 profile 层又写 relationship 层，而且每轮都写新行。同一事实会被反复写入几十次，读时才用 prune_recalled 去重。结果：存储冗余膨胀，去重压力全压在读路径。

短板 5：每轮 embed 两次的浪费

写路径对同一句话 embed 两次（relationship 层”用户：X” + profile 层”X”）。这是有意的（前缀影响向量语义），但确实每轮多付一次 embedding 成本。

短板 6：dreaming 是快照式，长会话只提炼一次

classified_at 盖章后永不重扫。一个聊了三个月的长会话，只在第一次空闲时被提炼一次，之后新出现的长期事实再也不会被提炼（只能靠每轮的原样埋点）。

启发

启发 1：重新划「记忆的共享边界」

这是最重要的一条，直接影响产品体验。建议分三级而不是现在的两级：

级 谁能访问 存什么
平台级 系统/推荐引擎 结构化画像（用于匹配、推荐），数字人不直接当”记得”用
关系级 这个用户 × 这个数字人 对话里学到的所有事，按数字人隔离
数字人自己的记忆 只有这个数字人 它自己的经历、设定、它”主动想记住”的

核心原则：「平台知道」≠「数字人记得」。 平台可以用画像做匹配，但数字人绝不能假装它知道没跟它聊过的事。raw-turn 的原文绝不该进平台级。

同时，对于每一个用户和数字人，也要存储「一个是原文，还有一个是提炼之后的消息」，这样检索起来就方便很多。

启发 2：必须有遗忘机制

记忆系统不能只有 upsert。至少加三层：

  • 时间衰减：检索时给记忆加权，越久远的越弱；
  • 重要性分级：核心事实（过敏、职业）常驻，琐碎闲聊自然淘汰；
  • 显式删除路径：既是合规要求（GDPR），也是产品要求（用户说”忘掉这段”）。

启发 3：检索要带「时间 + 重要性」，不能纯相似度

纯 top-K + 无阈值，在聊天产品里会召回过时或无关的东西。建议：

  • 相似度 + 时间衰减 + 重要性三者加权排序；
  • 加一个软阈值，低于阈值就宁可不注入（”宁缺毋滥”），避免数字人基于无关记忆胡说。
